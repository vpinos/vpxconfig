# VPXConfig
<img width="1279" height="798" alt="image" src="https://github.com/user-attachments/assets/f2aa7ac8-d59a-49bf-aa37-b2d286764670" />

A small local web app that walks you through the VPinballX settings for a three-screen cabinet and
writes a new ini file.

```
./run.py            # then open http://localhost:1111 in Chrome
```

- **Base:** by default `VPinballX.ini` in this folder (the default generated by `VPinballX_BGFX -h`, plus the settings VPXConfig manages that `-h` leaves out, such as the extra plugin sections; `VPinballX.ini.vpconfigbackup` is the original, and `tools/sync_base.py` adds anything missing). On the Start page you can pick an existing `VPinballX.ini` instead, using the built-in file browser (it lists the folders of the machine running this app, not the browser's) or by typing the full path; the wizard then fills its fields from that file and edits a copy. Blank means the project's file. When you load a file, a copy is saved next to it as `<name>.vpconfigbackup` (an existing backup with different content is never overwritten; a timestamped one is made instead, and if the backup can't be written the load fails). The base file is never modified, and the project's `VPinballX.ini` always defines the wizard's labels and defaults.
- **Output:** by default `~/.local/share/VPinballX/10.8/VPinballX.ini`, where VPX keeps its settings (VPX 10.8 uses a folder per minor version). On the Start page you can type another full path or Browse to override it, just like the base file. Review & Save writes it: an existing file is first copied next to itself as `<name>.vpconfigbackup` (never overwriting a different backup), its permissions are kept, missing folders are created, the page asks before replacing a file, and the project's own base `VPinballX.ini` can never be chosen. Keys the wizard doesn't cover are copied through unchanged from the base.
- **No dependencies:** running from source needs only Python 3.12+ and its standard library. The only fixed location is VPX's own settings file (the output default above); everything else is relative to this folder or chosen by you.
- **Local only:** listens on 127.0.0.1 by default (`--host` / `--port` to change). It runs a fixed set of read-only system commands (currently `wayland-info`) and can only write the chosen output file (plus its `.vpconfigbackup`), backups next to a loaded base file, and `state.json`.

## Running the executable

Each release has one archive per architecture, `vpxconfig-linux-x86_64.tar.gz` and `vpxconfig-linux-arm64.tar.gz`. Each holds a single file, `vpxconfig`, that needs no Python. The version is in the release's name and in `--version`:

```
tar -xzf vpxconfig-linux-x86_64.tar.gz
./vpxconfig          # then open http://localhost:1111 in Chrome
./vpxconfig --version
```

`--host` and `--port` work as above. Stop it with Ctrl+C, or with the **Quit** button at the bottom of the page's sidebar (it asks first; your answers are already saved as you type, but the ini file is only written when you click Write on the Review page). Add `--open-chrome` to have it open `google-chrome` on itself once it's up and close that window too when you quit (via the page's Quit button or Chrome's own close button) -- off by default, so a plain `./vpxconfig`/`./run.py` still just serves the page for you to open in any browser yourself. Next to the executable is a `.sha256` file to check the download. Because the executable unpacks itself into a temporary folder that is deleted when it exits, your answers are kept in `~/.config/vpxconfig/state.json` (or under `$XDG_CONFIG_HOME` if that is set) instead of next to the program. It is not signed.

## How it works

| Piece | File |
|---|---|
| Wizard steps and which keys each covers (one page per plugin, under a "Plugins" header) | `vpxconfig/steps.py`, `vpxconfig/plugins.py` |
| Label, help, default, range and dropdown options | read from the comments in `VPinballX.ini` |
| Line-preserving ini editor | `vpxconfig/ini.py` |
| System commands (monitor detection) | `vpxconfig/system.py` |
| Folder listing for the file browser | `vpxconfig/fs.py` |
| HTTP server and JSON API | `vpxconfig/server.py` |
| UI | `web/` |

Your answers are saved to `state.json` so a restart keeps them. A blank answer means "leave at the VPX default".
The output is always the whole base file with your changes applied. A value equal to VPX's own default is left blank (a blank value already means the default), so an untouched setting never gets an explicit value.

## Adding a setting

A setting is a `Setting(...)` (see `vpxconfig/settings.py`); `vpxconfig/steps.py` decides which page and group shows it.
Add one line to a group in `steps.py`:

```python
# Key that is in VPinballX.ini: label, help, default, options and range come from its comment.
S("Player", "BGSet")

# ...same, but overriding some of it:
S("Player", "PlayfieldFullScreen", label="Playfield FullScreen",
  options=[("0", "Disabled"), ("1", "Enabled")], description="Enable borderless fullscreen mode.")

# Key that is NOT in the template (e.g. written by a plugin): describe it fully.
S("Backglass", "Priority.PUP", type="int", label="PUP priority", default="0", min="0", max="9",
  description="Which content is shown on the backglass window.")
```

| Attribute | Meaning |
|---|---|
| `section`, `key` | where it lives in the ini |
| `label`, `description`, `notes` | what the user sees |
| `type` | `bool`, `int`, `float`, `text`, `select` or `display` (a monitor dropdown). Inferred for keys in the template |
| `default` | VPX's default; a blank ini value means this |
| `options` | acceptable values for `select`/`bool`: `[("0", "Disabled"), ("1", "Enabled")]` |
| `min`, `max` | acceptable range for `int`/`float` |
| `placeholder` | grey hint in an empty box (`""` for none) |
| `initial` | answer the wizard starts with (a suggestion; the user can change or clear it, and loading a base file replaces it) |

Anything left out is read from the comment above the key in `VPinballX.ini`. A key that isn't in that file must at least have a `type`.
Definitions are checked at startup (unknown type, default not among the options, min > max, duplicate keys, ...), and values are checked
against `options` / `min` / `max` on the Review page: an unacceptable value is listed and the file isn't written until it's fixed.
Your answers are stored in `state.json` as a flat `"Section.Key": "value"` map, so adding a setting needs no migration.

**Keep the base file in step:** a setting defined in code should also be in `VPinballX.ini` (with a comment in its format). Run `tools/sync_base.py` after adding a `Setting`; a test fails until the base file has the key. The tool adds the missing settings, and fills in the starting answers (`initial`) that differ from VPX's default (for example the ScoreView priorities), so that a fresh start compares equal to the base file and Review shows no changes. It never overwrites a value, and running it twice does nothing. If you regenerate `VPinballX.ini` with `VPinballX_BGFX -h`, run the tool afterwards to put the added settings back.

## Monitor detection

The Display fields list the monitors reported by `wayland-info -i output`. VPX gets a display's name from `SDL_GetDisplayName`, so the name is chosen the way SDL 3.4's Wayland driver does (`SDL_waylandvideo.c`): if the compositor advertises `wl_output` version 4 or newer, SDL uses the `wl_output` description and ignores the `xdg_output` one ("deprecated as of wl_output v4"); with an older `wl_output` it uses the `xdg_output` description; and when there is no description it falls back to the geometry line's `model`. On most compositors that is the same text as `grep -oP "description: '\\K[^']+"` prints, but not always, which is why the page says where the name came from. What is stored in `PlayfieldDisplay`, `BackglassDisplay` and `ScoreViewDisplay` is what VPX itself writes and compares exactly: the display name plus its position in the desktop layout, for example `LG HDR 4K [1920, 0]` (`Window.cpp` builds it as `"{name} [{x}, {y}]"`). A value without the position matches nothing, and VPX then falls back to the primary display. A value in the older form (description only) is recognised, with a note asking you to pick the monitor again. It uses the session's `WAYLAND_DISPLAY` first and then every other Wayland socket in `XDG_RUNTIME_DIR`, and understands both the quoted and the older unquoted output styles. If nothing is found, the page shows why and a "What was tried" section with the command's exit code, its stderr and the first lines of its output. Start VPXConfig from a terminal inside the desktop session (so it inherits `WAYLAND_DISPLAY`) and compare with `echo $WAYLAND_DISPLAY; ls $XDG_RUNTIME_DIR | grep wayland; which -a wayland-info`. You can always type the display name by hand.

## Adding a system command

Add a function to `COMMANDS` in `vpxconfig/system.py`. It is served at `/api/system/<name>`. Commands take no user input and run without a shell.

## Building the executable

```
tools/build.sh                                       # -> dist/vpxconfig and dist/vpxconfig.sha256
tools/smoke_test_exe.sh dist/vpxconfig
```

`tools/build.sh` installs PyInstaller (pinned in `requirements-build.txt`) into a virtual environment in `.venv/`, created on the first run, and never into the system Python. `vpxconfig.spec` says what is bundled: the `web/` folder and the base `VPinballX.ini`. The smoke test starts the executable with a throw-away home and config folder and checks the version, the pages, the wizard and where the answers are kept.

## Versioning and releases

The version is set in one place, `__version__` in `vpxconfig/__init__.py` (the first version is `0.5`). It is shown by `--version`, in the start-up message and in the page's sidebar. A release is named by a git tag `v<version>`, for example `v0.5`; the executable file itself is always just `vpxconfig`.

The `Release` workflow (`.github/workflows/release.yml`) builds on Ubuntu 22.04 for x86_64 and for arm64 (an older glibc, so the executable runs on older distributions too), runs the unit tests, smoke tests each executable, and can publish a GitHub release with both archives, their `.sha256` files and generated release notes. Only Linux is built: the wizard uses Linux tools (`wayland-info`) and VPX's Linux settings location. There are two ways to run it:

- **Push a tag.** Set `__version__` (skip this for `0.5`, which is already set), commit, then `git tag v0.5 && git push origin v0.5`. The workflow first checks that the tag matches `__version__`; a mismatch fails before anything is built. It then builds and publishes the release.
- **Run it by hand.** On GitHub go to Actions, Release, Run workflow, and type the **version** (for example `0.5`). That version is put into the code for that run only, so the executable reports it without you editing anything, and the run builds, tests and uploads each archive as a workflow artifact. Tick **Publish** as well to also create the release `v<version>` (and its tag, on the commit that was run). Publish is off by default, and a version that already has a release is refused before the build starts.

To check a download: `sha256sum -c vpxconfig-linux-x86_64.tar.gz.sha256`, or the arm64 one.
